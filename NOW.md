# Что делаем сейчас

Задача для Claude Code. Основа — ветка `feat/skeleton` (сквозной каркас на симуляторе).
Реальная стойка по-прежнему не подключена: этап 0 в отчётах остаётся «не проверено на стойке».

Две части, две ветки, два PR. Часть 2 начинать после слияния части 1.

**Схема развёртывания.** Система будет сервисом для многих предприятий-клиентов: одна установка,
общая база, клиенты разделены по организации фильтром в API. Мониторинг идёт в комплексе с
аварийным ремонтом и контролем геометрической точности, поэтому сотрудники сервисной компании
видят станки всех клиентов (роль `service`).

## Часть 1. Укрепление ядра данных — ветка `feat/harden-core`

Цель: цифрам таймлайна и OEE можно доверять после любых сбоев и перезапусков.

| № | Что сделать | Критерий готовности |
|---|---|---|
| 1.1 | Отметку «с какого момента пересчитать OEE» хранить в БД (по образцу `timeline_dirty`), а не в памяти `worker` | Тест: перезапуск `worker` между перестройкой таймлайна и расчётом OEE не теряет пересчёт |
| 1.2 | Брак в `oee_hourly` не обрезать до числа деталей этого часа | Тест: качество за смену и за сутки (сумма часов) совпадает |
| 1.3 | Сжатие `telemetry` через 30 дней; буфер edge не дольше 7 дней; правило записать в `ARCHITECTURE.md` | Новая миграция Alembic, старая не правится |
| 1.4 | Закрепить образ `timescaledb` на конкретной версии | В compose нет тега `latest` |
| 1.5 | Пересчёт за закрытый период `[from, to]` с корректной стыковкой на границе `to` | Тест: пересчёт середины истории не меняет интервалы после `to`; повторный пересчёт даёт тот же результат |
| 1.6 | Автоматический пересчёт при изменении смен, норм цикла, правил состояний, причин простоя | Изменение справочника через API ставит отметку пересчёта; ручной `make recalc` не нужен |
| 1.7 | `worker` не меняет записи оператора: окончание причины простоя вычисляется при чтении | В `worker` нет UPDATE таблиц пользовательского ввода |
| 1.8 | Нормы цикла с учётом `valid_from` | Тест: смена нормы не меняет OEE за прошлые периоды |
| 1.9 | Интеграционные тесты на реальной БД и брокере (testcontainers): edge → MQTT → ingest → worker → OEE | Сценарии: обычная работа; брокер недоступен 10 минут; перезапуск коллектора с непустым буфером. Разрывов `seq` нет, OEE совпадает с эталоном |
| 1.10 | Проверка разрывов `seq` на сервере | Разрыв виден в логе и в API состояния коллектора |

Отчёт: `docs/harden-core-report.md`.

## Часть 2. Организации, площадки и роли — ветка `feat/tenancy-roles`

Цель: система различает, чьи данные и кто их может видеть. Экраны управления пользователями
делаются минимальными.

### 2.1. Иерархия

```
Организация → Площадка (завод) → Участок (цех) → Станок
```

- Новая таблица `organizations`; `sites.org_id` обязателен.
- Станок: внутренний ключ (bigint или UUID) + поле `code`; уникальность `(site_id, code)`.
  Все таблицы, ссылающиеся на станок, переходят на внутренний ключ.
- Справочники (смены, причины простоя и брака, нормы цикла, правила состояний) привязаны к
  площадке; значения по умолчанию можно задать на уровне организации.
- Seed: одна организация, две площадки с разными часовыми поясами, по два участка.

### 2.2. MQTT и коллекторы

- Топики: `mm/v1/{org}/{site}/{machine_code}/telemetry|event`,
  `mm/v1/{org}/{site}/collector/{collector_id}/heartbeat`. Меняется прямо в `v1`: развёрнутых
  коллекторов нет.
- У каждого коллектора своя учётная запись брокера; ACL разрешает запись только в топики своей
  площадки.
- `ingest` определяет организацию и площадку по коллектору из справочника и сверяет с топиком.
  Несовпадение — сообщение в `ingest_rejects`.
- Авторегистрацию станков оставить, но только внутри площадки своего коллектора.
- Симулятор: два коллектора на разных площадках.

### 2.3. Пользователи и роли

Таблицы:

```
users:        id, login, password_hash, full_name, is_active, is_superadmin
memberships:  id, user_id, role, org_id, site_id (null), area_id (null)
```

Роль выдаётся на узел иерархии: только `org_id` — вся организация, с `site_id` — площадка,
с `area_id` — участок. У пользователя может быть несколько строк.

| Роль | Доступ |
|---|---|
| `operator` | Экран своего станка: причина простоя, брак, наладка |
| `master` | Свой участок: дашборд, правка причин простоя и брака, отчёты |
| `engineer` | Площадка: нормы цикла, программы, аналитика |
| `admin` | Организация: станки, смены, справочники, пользователи |
| `service` | Сотрудник сервисной компании: станки, состояния, аварии и наработка по всем организациям |
| суперадмин | Все организации, создание организаций |

Настраиваемую матрицу прав не делать: права ролей заданы в коде одной таблицей.

### 2.4. Проверка доступа

- Одно место: зависимость API по токену вычисляет набор доступных станков и роль на каждом узле.
- Каждый маршрут и WebSocket `/ws/live` фильтруются этим набором. Доступ к чужому объекту
  возвращает 404, а не 403.
- Сервисные функции принимают область доступа явным параметром; запросов к данным в обход неё нет.
- Канал Redis для live — на площадку: `live.{org}.{site}`.

### 2.5. Киоски

- Токен устройства привязан к одному станку (экран оператора) или к одному участку (ТВ-дашборд).
  Общий токен из `.env` убрать.
- Токен хранится в БД в виде хеша, выдаётся и отзывается администратором.
- В записях оператора поле `operator` остаётся текстовым; табельный номер и PIN — позже.

### 2.6. Интерфейс (минимум)

- `/login` — вход по логину и паролю.
- В админке: список пользователей, выдача ролей на узел иерархии, выдача и отзыв токенов киосков.
- Переключатель площадки и участка в дашборде и аналитике, если у пользователя их несколько.
- Меню показывает только разделы, доступные по роли.

### 2.7. Тесты

- Пользователь одной организации не видит станки, таймлайн, OEE и справочники другой:
  по каждому маршруту API и по WebSocket.
- Мастер участка не видит соседний участок; технолог видит всю площадку.
- Коллектор не может записать данные в чужую площадку.
- Токен киоска станка не открывает другой станок и админские маршруты.

Отчёт: `docs/tenancy-roles-report.md`. Архитектурные решения — ADR 0003 (иерархия и ключ станка)
и ADR 0004 (модель ролей). `ARCHITECTURE.md` обновить: система становится сервисом для многих
клиентов.

## Что сейчас не делаем

| Что | Почему |
|---|---|
| Проба FOCAS на реальной стойке | Ждёт доступа к станку и библиотеке Fanuc |
| PIN и табельные номера операторов | После каркаса ролей |
| LDAP / SSO, журнал действий пользователей | Отдельным этапом |
| Сервисный модуль: заявки на ремонт из аварий, обслуживание по наработке, протоколы геометрической точности | Следующий этап, после ролей и изоляции |
| Row-level security в БД, журнал входов сервисных инженеров, согласие клиента на доступ | Избыточно на этом этапе; достаточно фильтра по организации в API |
| TLS на брокере, Prometheus, бэкапы, установщик Windows | Этап эксплуатации, перед подключением первого внешнего клиента |
| Уведомления, экспорт отчётов, тренды | После укрепления ядра |
