# Архитектура платформы мониторинга станков с ЧПУ

Система промышленного мониторинга и производственной аналитики (класс MachineMetrics):
от опроса стойки Fanuc 0i-MD до расчёта OEE, экрана оператора и цехового дашборда.

**Модель развёртывания — сервис для многих предприятий-клиентов.** Одна установка и общая база;
данные клиентов разделены по организации фильтром доступа в API (п. 7.3). Мониторинг идёт в комплексе с
аварийным ремонтом и контролем геометрической точности, поэтому сотрудники сервисной компании
(роль `service`) видят станки всех клиентов. Иерархия: **организация → площадка → участок → станок**
(ADR 0003), права — роли на узлах этой иерархии (ADR 0004).

---

## 1. Ключевые принципы

1. **Сырые данные неизменяемы.** Всё производное (таймлайн состояний, OEE, отчёты) можно пересчитать из сырых данных в любой момент — при смене норм цикла, правил состояний, границ смен. Оригиналы измерений (файлы `.b5r` и PDF-отчёты ballbar) хранятся всегда: их нельзя изменить или удалить.
2. **Таймлайн состояний — центральная сущность.** OEE и почти вся аналитика считаются из интервалов состояний (RUN / IDLE / STOP / ALARM / SETUP / OFFLINE), а не из сырых точек.
3. **Edge «тупой и надёжный».** Коллектор только читает стойку, ставит метку времени и доставляет данные. Никакой бизнес-логики.
4. **Ни одной потерянной секунды.** Store-and-forward буфер на edge, идемпотентный приём на сервере, явное состояние `OFFLINE` вместо дыр.
5. **Время — с источника.** Метка времени ставится на edge в момент чтения со стойки (UTC). NTP на всех узлах.
6. **Контракт edge↔сервер версионирован** (JSON Schema в `shared/schemas`). Новые типы стоек = новые драйверы, сервер не меняется.
7. **Модульный монолит.** Один backend-кодбейз с изолированными модулями; запускается несколькими процессами (api, ingest, worker). Микросервисы — только при реальной необходимости.
8. **Одна БД.** PostgreSQL + TimescaleDB для временных рядов и справочников.
9. **Симулятор с первого дня.** Вся цепочка тестируется без реальных станков.
10. **Изоляция клиентов в одном месте.** Набор доступных станков и роль на каждом узле вычисляются одной зависимостью API по токену; сервисные функции получают область доступа явным параметром. Чужой объект для клиента не существует (404).

## 2. Общая схема (4 контура)

```

┌──────────────────────────┐        ┌──────────────────────────────────────────────┐

│  │  └ simulator          │        │  backend: ingest ──▶ raw hypertables         │
│  ├ poller (поток/станок) │        │        │  отметка «данные изменились»        │
│  ├ buffer (SQLite)       │        │        ▼                                     │
│  └ publisher (MQTT)      │        │  backend: worker ──▶ state_intervals,        │
└──────────────────────────┘        │          part_events, OEE; live ──▶ Redis    │
       │ FOCAS/Ethernet :8193       │        │                                     │
       ▼                            │  backend: api (REST + WebSocket) ◀── Redis   │
 Fanuc 0i-MD × N                    │        │                                     │
                                    │        ▼                                     │
                                    │  frontend (nginx): operator / dashboard /    │
                                    │    analytics / alarms / repairs / service /  │
                                    │    admin                                     │
                                    │  timescaledb · redis                         │
                                    └──────────────────────────────────────────────┘
```

| Контур | Назначение | Компоненты |
|---|---|---|
| 1. Сбор (Edge) | Опрос стоек, буферизация, доставка | `edge/` (Python), драйвер FOCAS, SQLite-буфер |
| 2. Приём и хранение | Брокер, проверка и запись сырых данных, хранение | Mosquitto, `backend/app/ingest`, TimescaleDB, Redis |
| 3. Аналитика | Таймлайн, циклы, OEE, простои, брак, отчёты, журнал аварий, ремонт и ТО, архив геометрии | `backend/app/timeline`, `oee`, `reports`, `repairs`, `geometry` (уведомления `notify` — запланированы) |
| 4. Представление | API, экран оператора, цеховой ТВ-дашборд, админка | `backend/app/api`, `frontend/` |

## 3. Контур 1 — Edge-коллектор

### 3.1. Назначение
Опрашивает N станков, ставит метку времени, кладёт в локальный буфер, публикует в MQTT. Работает автономно при отсутствии связи с сервером.

### 3.2. Платформы
- **Windows (основной вариант в цеху):** Python 3.12, `Fwlib64.dll` (FOCAS2) вместе с `fwlibe64.dll` и `fwlib0iD64.dll` в одной папке — коллектор ставит её первой в `PATH` процесса. Запланировано: упаковка PyInstaller → `.exe`, запуск как службы Windows (NSSM или pywin32); пока коллектор и проба запускаются из Python. Если на объекте доступна только `Fwlib32.dll` — 32-битный Python.
- **Linux:** `libfwlib32.so` (x86 / ARM, из Fanuc FOCAS Linux library), запуск в Docker (образ `edge/Dockerfile`) или systemd.
- Библиотеки FOCAS **не хранятся в репозитории** (лицензия Fanuc) — кладутся в `edge/vendor/` вручную, путь задаётся в конфиге.

### 3.3. Структура
```
edge/
├── collector/
│   ├── main.py              # точка входа, загрузка конфига, запуск пулеров
│   ├── config.py            # pydantic-модель конфига (YAML)
│   ├── drivers/
│   │   ├── base.py          # интерфейс MachineDriver
│   │   ├── fanuc_focas.py   # ctypes-обёртка над Fwlib
│   │   └── simulator.py     # эмулятор станка
│   ├── poller.py            # цикл опроса одного станка (поток)
│   ├── buffer.py            # SQLite store-and-forward
│   ├── publisher.py         # MQTT (paho-mqtt), QoS 1, переотправка из буфера
│   └── health.py            # heartbeat коллектора, метрики
├── tools/focas_probe.py     # этап 0: проверка связи со стойкой
├── vendor/                  # Fwlib*.dll / libfwlib32.so (в .gitignore)
├── config.example.yaml
└── Dockerfile
```

### 3.4. Интерфейс драйвера
```python
class MachineDriver(Protocol):
    def connect(self) -> None: ...
    def disconnect(self) -> None: ...
    def read_snapshot(self) -> MachineSnapshot: ...   # все сигналы за один опрос
    def read_alarms(self) -> list[Alarm]: ...
```
Реализации: `FanucFocasDriver`, `SimulatorDriver`; позже `OpcUaDriver`, `MTConnectDriver`, `SiemensDriver`.

### 3.5. Сигналы Fanuc 0i-MD (FOCAS2)
Система по отношению к стойке **только читает**: функций записи в ЧПУ (`cnc_wr*`, `pmc_wr*`, загрузка и
удаление программ) нет ни в коллекторе, ни в пробе. Пока не измерено, как стойка переносит опрос, коллектор
читает минимум (ADR 0007); набор — `signals` в конфиге станка.

| Сигнал (`signals`) | Функция FOCAS | Когда читается |
|---|---|---|
| Подключение | `cnc_allclibhndl3(ip, 8193, timeout)` / `cnc_freelibhndl` | — |
| `status`: aut, run, motion, mstb, emergency, alarm, edit | `cnc_statinfo` | всегда, каждый опрос |
| `program`: номер (основная / выполняемая) и имя | `cnc_rdprgnum`, `cnc_exeprgname` (если поддерживается) | по умолчанию |
| `part_count`: счётчик деталей | `cnc_rdmacro(#3901)` или `cnc_rdparam(6711)` — настраивается | по умолчанию |
| `alarms`: аварии | `cnc_rdalmmsg2` | по умолчанию, только при `alarm != 0` |
| `feed_actual`: фактическая подача | `cnc_actf` | только если включён явно |
| `spindle_speed`: фактические обороты | `cnc_acts` | только если включён явно |
| `spindle_load`: нагрузка шпинделя | `cnc_rdspmeter` | только если включён явно |

Период опроса — 1 с по умолчанию, допускается 2–5 с. Коррекции (`pmc_rdpmcrng` G0012/G0030/G0014),
инструмент (#4120), таймеры (`cnc_rdtimer`), нагрузки осей (`cnc_rdsvmeter`), `cnc_rddynamic2` коллектор
не читает: их один раз смотрит разведка пробы `--recon` (`docs/runbooks/first-machine.md`).

Требования к стойке: встроенный Ethernet, FOCAS2 включён, порт 8193 доступен из сети коллектора. **Этап 0 проекта — проверить всё это скриптом `focas_probe.py` на реальной стойке.**

### 3.6. Поведение
- Один поток на станок; общий publisher. Публикуются только поля настроенных сигналов.
- Ошибка FOCAS → переподключение с экспоненциальной задержкой (1 → 30 с); публикуется событие `connection: lost/restored`.
- Публикация телеметрии: **по изменению + не реже 1 раза в 10 с** (keyframe). Счётчик деталей и статус — всегда при изменении.
- Буфер SQLite: каждое сообщение пишется в буфер до отправки; удаляется после PUBACK. Срок хранения — **не дольше 7 дней** (`buffer.max_age_days`, значения больше 7 конфиг не принимает); более старые сообщения вытесняются.
- **Правило сроков:** буфер edge ≤ 7 дней < сжатие `telemetry` через 30 дней. Опоздавшие данные никогда не попадают в сжатый чанк. Менять один срок без другого нельзя.
- Heartbeat коллектора каждые 15 с (версия, аптайм, размер буфера, статусы подключений).

## 4. Контракт сообщений (MQTT)

### 4.1. Топики
```
mm/v1/{org}/{site}/{machine_code}/telemetry     # снимок сигналов
mm/v1/{org}/{site}/{machine_code}/event         # аварии, подключение/отключение, смена программы
mm/v1/{org}/{site}/collector/{collector_id}/heartbeat
```
`{org}` и `{site}` — коды организации и площадки, `{machine_code}` — код станка, уникальный внутри площадки.
Heartbeat несёт `epoch` — случайный идентификатор, созданный вместе с буфером коллектора. Новая эпоха
означает, что буфер потерян: неотправленные данные утрачены, счётчики `seq` начаты заново.
QoS 1, `retain=false` (кроме heartbeat — `retain=true`). Схемы — `shared/schemas/*.json` (JSON Schema draft 2020-12).

### 4.2. Конверт
```json
{
  "schema": "telemetry.v1",
  "msg_id": "0192f3b4-7c1e-7a3d-9f00-1a2b3c4d5e6f",
  "collector_id": "edge-shop1",
  "machine_id": "m07",
  "ts": "2026-11-16T19:01:02.345Z",
  "seq": 184223,
  "data": { }
}
```
- `msg_id` — UUIDv7, ключ идемпотентности на сервере.
- `ts` — время чтения со стойки (UTC, edge).
- `seq` — монотонный счётчик на станок; разрыв последовательности = потеря данных (логируется).

### 4.3. `telemetry.v1` → `data`
```json
{
  "connected": true,
  "mode": "MEM",
  "run": "START",
  "motion": true,
  "emergency": false,
  "alarm": false,
  "program": "O1234",
  "program_name": "O1234",
  "feed_actual": 1250.0,
  "spindle_speed": 8000,
  "spindle_load": 37.5,
  "feed_override": 100,
  "spindle_override": 100,
  "part_count": 15873
}
```

### 4.4. `event.v1` → `data`
```json
{ "type": "alarm_raised", "code": "SV0401", "message": "...", "category": "servo" }
```
Типы: `alarm_raised`, `alarm_cleared`, `connection_lost`, `connection_restored`, `program_changed`.

## 5. Контур 2 — Приём и хранение

### 5.1. Mosquitto
- Коллекторы подключаются по TLS на 8883 (prod, ADR 0010): сертификат — тот же, что Caddy получил для домена
  (Mosquitto читает его из тома Caddy и перечитывает продлённый по SIGHUP). 1883 без TLS — только внутри сети
  compose (`ingest`, симуляторы). В prod пароли `change-me…` не принимаются.
- У каждого коллектора своя учётная запись (`MM_MQTT_COLLECTORS`);
  ACL разрешает ему запись только в `mm/v1/{org}/{site}/+/telemetry|event` своей площадки и в свой heartbeat,
  чтение — ничего. Backend — только читает.
- Persistence включён, `autosave_interval 5`: при аварийном падении брокера теряются не более 5 последних
  секунд сообщений, ещё не доставленных `ingest`.

### 5.2. Модуль `ingest` (процесс backend)
1. Подписка на `mm/v1/#`: обычная, с постоянной сессией MQTT. Shared subscription не используется: Mosquitto не восстанавливает её после собственного перезапуска, и сообщения, пришедшие раньше переподключения `ingest`, теряются. Один экземпляр `ingest`; масштабирование — разбиением топиков, отдельным решением.
2. Валидация по JSON Schema; невалидное → `ingest_rejects` + метрика.
   Коллектор должен быть зарегистрирован; организация и площадка топика должны совпадать с площадкой коллектора
   из справочника, иначе сообщение уходит в `ingest_rejects`. Новый станок регистрируется автоматически,
   но только внутри площадки своего коллектора. Справочники коллекторов и станков `ingest` держит в памяти
   и перечитывает раз в 30 с (`MM_INGEST_DIRECTORY_REFRESH_S`) и сразу при незнакомом коллекторе:
   перенесённый на другую площадку или удалённый коллектор перестаёт писать на старое место не позже чем
   через 30 с.
3. Идемпотентная запись: `INSERT ... ON CONFLICT (msg_id, ts) DO NOTHING` (ключ включает `ts` — требование hypertable, см. ADR 0001). PUBACK брокеру — только после `COMMIT` (ADR 0002).
4. `ingest` ничего не выводит из данных: в той же транзакции он ставит отметку `timeline_dirty` — «данные станка изменились с такого-то момента». Опоздавшие данные из буфера edge обрабатываются тем же путём.
5. Таймлайн, детали, OEE и live-состояние в Redis строит `worker` (п. 6.2).
6. Проверка разрывов `seq`: вычисляется по сырым данным (`worker` пишет в лог, API `/collectors` показывает). Дыра считается разрывом, если не закрылась за 60 с.

### 5.3. Модель данных (PostgreSQL + TimescaleDB)

**Иерархия и справочники**
| Таблица | Ключевые поля |
|---|---|
| `organizations` | id, code (уникален), name |
| `sites` | id, org_id (обязателен), code (уникален в организации), name, timezone |
| `areas` | id, site_id, name |
| `machines` | id (bigint, внутренний ключ), site_id, code (уникален в площадке), area_id, name, controller_type, collector_id, state_rules_id, is_active, cycle_pause_threshold_s, passport_code (код QR-наклейки: 8 знаков, уникален, выдаёт `new_passport_code()` — ADR 0009) |
| `collectors` | id, site_id, name, last_heartbeat, version, epoch, buffer_lost_at |
| `state_rules`, `shift_templates`, `downtime_reasons`, `scrap_reasons`, `programs` | org_id + site_id (null = значение по умолчанию для всех площадок организации); у `programs` ещё machine_id и valid_from |
| `users` | id, login, password_hash, full_name, is_active, is_superadmin |
| `memberships` | user_id, role, org_id, site_id (null), area_id (null) — роль на узле иерархии |
| `device_tokens` | token_hash, name, machine_id **или** area_id, created_by, revoked_at |

Справочник площадки: если у площадки есть свои строки справочника, действуют они, иначе — строки
организации по умолчанию. Норма цикла станка важнее нормы площадки, та — нормы организации.
Все таблицы, ссылающиеся на станок, ссылаются на внутренний ключ `machines.id`.

**Сырые данные (hypertables, неизменяемые)**
| Таблица | Поля | Политики |
|---|---|---|
| `telemetry` | ts, machine_id, msg_id (PK: msg_id + ts), seq, collector_id, connected, mode, run, motion, alarm, emergency, program, feed, speed, load, overrides, part_count, received_at | chunk 1 день, compression > 30 дней, retention 1–2 года |
| `machine_events` | ts, machine_id, msg_id (PK: msg_id + ts), seq, collector_id, type, code, message, payload jsonb | retention 3 года |

**Производные данные (пересчитываемые)**
| Таблица | Поля |
|---|---|
| `state_intervals` | id, machine_id, state, start_ts, end_ts (null = открыт), program, rules_version |
| `part_events` | ts, machine_id, program, delta (из приращения part_count, с обработкой сброса счётчика) |
| `cycles` | machine_id, end_ts (деталь), start_ts (предыдущая деталь), program, parts, machine_s (RUN), gap_s (от детали до запуска), idle_s / stop_s / alarm_s / setup_s (прерывания после запуска), offline_s, kind (normal / setup / incomplete) — п. 6.3, ADR 0008 |
| `oee_hourly`, `oee_shift` | machine_id, period_start, planned_time_s, run_time_s, idle_s, stop_s, alarm_s, offline_s, total_parts, good_parts, ideal_time_s, availability, performance, quality, oee, calc_version |

**Пользовательский ввод**
| Таблица | Поля |
|---|---|
| `downtime_annotations` | id, machine_id, start_ts, end_ts, reason_id, comment, operator, created_at |
| `scrap_records` | id, machine_id, ts, program, qty, reason_id, operator |
| `operator_setup_marks` | id, machine_id, start_ts, end_ts, operator (ручная отметка «наладка») |
| `repair_requests` | id, machine_id, status, description, alarm_ts + alarm_code (авария, из которой открыта), failure_ts, исполнитель, моменты шагов (указанный и записи в систему), work_done, voided_at + void_reason |
| `repair_request_history` | request_id, ts (указанный момент), recorded_at (момент записи), action, executor_id, user_name, comment |
| `repair_records` | id, machine_id, completed_at, description, engineer, request_id (null — ремонт вне системы), voided_at + void_reason |
| `maintenance_plans`, `maintenance_records` | регламент «каждые N часов RUN» станка; отметки о выполнении (аннулируются с причиной) |

`operator` — текстовое поле; табельный номер и PIN оператора — отдельным этапом. Время реакции и
восстановления заявок и наработка по регламентам не хранятся — вычисляются по таймлайну при чтении (п. 6.5).

Аннотации привязаны ко **времени**, а не к id интервала, — поэтому переживают пересчёт таймлайна.
Таблицы пользовательского ввода меняет только пользователь. Причина простоя без окончания действует до следующего запуска станка; это окончание вычисляется при чтении (представление `downtime_annotations_resolved`), `worker` записи не трогает.

### 5.4. Правила определения состояний (по умолчанию, настраиваемые)
Порядок проверки — сверху вниз, первое совпадение:
| Состояние | Условие |
|---|---|
| `OFFLINE` | нет данных > 30 с или `connected=false` |
| `ALARM` | `alarm=true` или `emergency=true` |
| `SETUP` | активна отметка оператора «наладка» (или режим EDIT/MDI/JOG > N мин — опционально) |
| `RUN` | `run=START` и `mode=MEM`/`DNC` |
| `IDLE` | не RUN, длительность < `idle_to_stop_threshold` (по умолчанию 2 мин) |
| `STOP` | не RUN, длительность ≥ порога → требует причину от оператора |

`FEED HOLD` (`run=HOLD`) трактуется как не-RUN. Интервалы короче `min_interval` (5 с) сливаются с соседними (антидребезг).

### 5.5. Redis
- `machine:{id}:live` — текущий снимок + текущее состояние + начало состояния + счётчики смены.
- Pub/Sub `live.{org}.{site}` — поток изменений площадки для WebSocket; API пересылает клиенту только
  станки из его области доступа.
- Только кэш: потеря Redis не теряет данных.

## 6. Контур 3 — Аналитика

### 6.1. Расчёт OEE
Для периода (час / смена / сутки) и станка:

- **Planned Production Time (PPT)** = длительность смены − плановые перерывы − простои с причинами категории `planned`.
- **Run Time** = Σ `RUN` в пределах PPT.
- **Availability** = Run Time / PPT
- **Performance** = Σ(ideal_cycle_time(program) × parts) / Run Time
  (по каждой программе своя норма; если нормы нет — Performance не считается, период помечается `no_standard`; значение > 100% не обрезается, а подсвечивается как признак неверной нормы)
- **Quality** = (total_parts − scrap) / total_parts
- **OEE** = A × P × Q

Периоды вне смены (нерабочее время) в OEE не входят, но отображаются в таймлайне.

### 6.2. Модуль `worker` (процесс backend)
- Раз в несколько секунд по каждому станку: достройка таймлайна (`state_intervals`, `part_events`), затем OEE, затем live-состояние в Redis.
- **Отметки пересчёта хранятся в БД**, а не в памяти: `timeline_dirty` и `oee_dirty` («пересчитать с такого-то момента»). Отметка снимается в той же транзакции, что и пересчёт, поэтому перезапуск `worker` в любой момент ничего не теряет. Длинные периоды обрабатываются кусками по суткам.
- Отметки ставят: `ingest` (новые и опоздавшие данные), ввод оператора (причины, брак, наладка), изменение справочников через API (смены, нормы цикла, правила состояний, причины простоя) — на глубину `MM_RECALC_HORIZON_DAYS` (31 день).
- **Пересчёт вручную**: `make recalc from=… [to=…] [m=…]`. С `to` пересчитывается закрытый период: интервалы после `to` не меняются, на границе выполняется стыковка.
- Норма цикла действует с `valid_from` до следующей нормы той же программы; изменение нормы не меняет прошлые периоды.
- Брак учитывается по времени ввода и не обрезается числом деталей часа: сумма часов даёт то же качество, что смена.
- Уведомления (`notify`): простой > N мин без причины, авария, коллектор offline → Telegram / email / webhook.

### 6.3. Отчёты
- OEE по станкам / участкам / сменам, тренды.
- **Циклы по программам** (ADR 0008). Цикл — от детали до соседней детали той же машины; рост счётчика сразу
  на несколько деталей — один цикл (с учётом `parts_per_cycle` нормы). Внутри: машинное время (RUN), смена
  заготовки (от детали до следующего начала RUN), прерывания (IDLE, STOP, ALARM, SETUP после запуска).
  Промежуток от детали до запуска длиннее порога — простой, а не смена заготовки; порог — настройка станка
  `cycle_pause_threshold_s`, по умолчанию 3 × медиана машинного времени программы, не меньше 10 мин, и
  применяется при чтении. Первая деталь после смены программы — наладка, цикл с OFFLINE внутри — неполный;
  в статистику они не входят. Цикл относится к смене, в которой завершена деталь. `cycles` строится в
  `timeline.rebuild` вместе с таймлайном и пересчитывается вместе с ним. Аналитика: медианы и гистограммы
  машинного времени и смены заготовки, доля прерываний, сравнение с нормой цикла, по сменам и дням
  (`GET /cycles/stats`); на экране оператора — последний цикл и норма.
- Парето простоев по причинам, по времени и по количеству.
- Таймлайн (Gantt) по станкам за период.
- Выпуск: план/факт по сменам, брак по причинам.
- Экспорт CSV/XLSX.

### 6.4. Геометрическая точность — внутренний архив сервиса (модуль `geometry`, ADR 0005)
- **Только для сервиса.** Права на архив есть только у роли `service` и суперадмина; для пользователей
  клиента все маршруты архива отвечают 404, даже по своим станкам.
- **Тест ballbar** (Renishaw QC20, Ballbar 20) в карточке станка: дата, инженер, плоскость (XY/YZ/ZX), радиус,
  подача, дуга (360°/220°), температура воздуха и станка, шаблон теста, примечание. Ошибочный тест не
  удаляется, а аннулируется с причиной и выпадает из тренда.
- **Результаты** вводятся вручную — набор параметров с единицами из каталога (`app/geometry/catalog.py`):
  ISO 230-4 (круглость, круговое отклонение, круговой гистерезис) и диагностика Renishaw
  (неперпендикулярность, люфт, реверсивные пики, боковой зазор, циклическая ошибка, ошибка масштаба,
  прямолинейность — по осям плоскости; рассогласование приводов).
- **Оригиналы** (`.b5r`, PDF-отчёт) — в PostgreSQL (`ballbar_files`), до 25 МБ; триггер запрещает UPDATE и DELETE.
- **Сырые точки круга** — `ballbar_traces` (углы и радиальные отклонения на направление прохода), загружаются
  через API импорта; при их наличии в карточке рисуется полярный график.
- **Тренд параметра** — по тестам одного шаблона, а без шаблона — с одинаковыми плоскостью, радиусом,
  подачей и дугой. События на графике: отметки «столкновение» (`collision_marks`, ставят оператор и мастер)
  и выполненные ремонты (`repair_records`, ведёт сервис). Ошибочную отметку или запись о ремонте сервис
  аннулирует с причиной, как тест: она остаётся в списке зачёркнутой и не показывается на тренде.
- **Карточка станка** показывает дату последнего теста и сколько дней прошло; экран «Сервис» — список станков
  с этими же данными. Анализа нет: ни допусков, ни статусов, ни расчёта следующей проверки; разбор `.b5r`
  отложен.
- Журнал ремонтов (`repair_records`) ведёт модуль `repairs` (п. 6.5); архив показывает его записи на тренде.

### 6.5. Ремонт и обслуживание (модуль `repairs`, журнал аварий в `reports`, ADR 0006)
- **Журнал аварий** — эпизоды из сырых `machine_events`: от `alarm_raised` до `alarm_cleared` того же кода;
  повторное объявление открытой аварии нового эпизода не начинает, потерянный сброс закрывается первой
  выборкой телеметрии без аварии. Код, текст, категория, начало, длительность, «активна»; частота по станку
  (число, в сутки, суммарная длительность, по кодам); телеметрия за 10 минут до аварии и события в этом окне.
  Читается на запрос, ничего не хранит; индекс `ix_machine_events_alarms`.
- **Заявка на ремонт** — из аварии журнала одной кнопкой (ссылка на аварию по времени и коду, одна заявка на
  аварию) или вручную с моментом отказа. Статусы строго `новая → принята → в работе → выполнена`; принятие
  назначает исполнителя с ролью `service`, его можно сменить до выполнения. История действий —
  `repair_request_history`. Шаг хранит указанное время и момент записи в систему; шаг, внесённый задним
  числом больше чем на 30 минут, клиент видит с пометкой «время указано задним числом». Выполнение создаёт запись в журнале ремонтов со ссылкой на заявку; ручной ввод
  ремонтов вне системы остаётся. Ошибочную заявку аннулируют с причиной: клиент — пока она новая, сервис —
  до выполнения.
- **Время реакции и восстановления** вычисляются при чтении по таймлайну: реакция — от отказа до начала работ,
  восстановление — от отказа до первого RUN (ноль, если станок в момент отказа работал).
- **Обслуживание по наработке** — регламенты «каждые N часов RUN» на станок; наработка по таймлайну с
  последнего выполнения, статусы «в норме / скоро (от 90 %) / пора», прогноз даты по средней наработке
  за 30 дней. Напоминания (скоро и пора) — на экране «Сервис». Отметка о выполнении аннулируется с причиной.
- Клиент (мастер, технолог, администратор) видит заявки и график обслуживания своих станков и создаёт заявки;
  ведёт заявки и регламенты только сервис. Архив геометрии клиенту по-прежнему не виден.

## 7. Контур 4 — Представление

### 7.1. API (FastAPI)
- REST `/api/v1/...`: machines, timeline, oee, reasons, annotations, scrap, shifts, programs, reports, admin, auth;
  журнал аварий `alarms`, заявки `repair-requests`, обслуживание `maintenance` (п. 6.5); архив геометрии (п. 6.4);
  QR-паспорт `passport` (ниже).
- **QR-паспорт станка** (ADR 0009). У станка постоянный случайный код `passport_code`; наклейка ведёт на
  `https://<host>/m/<код>`, в QR только ссылка. `GET /passport/{code}` — куда ведёт наклейка по правам вызывающего:
  `service` (карточка станка), `machine` (страница `/m/<код>`), `operator` (экран оператора); неверный код и станок
  вне области доступа — одинаковый 404, без входа — 401. Администратор площадки: `POST /admin/machines/{id}/passport`
  — новый код (старая наклейка перестаёт работать), `GET /admin/machines/{id}/passport.pdf` — наклейка 90 × 50 мм,
  `GET /admin/areas/{id}/passports.pdf` — лист A4 наклеек участка. Адрес на наклейке — `MM_PUBLIC_URL`, иначе адрес
  запроса (`X-Forwarded-Host` / `X-Forwarded-Proto` от nginx).
- WebSocket `/ws/live?token=...` — изменения live-состояния станков из области доступа.
- Вход: больше 5 неудачных попыток за минуту по паре адрес + логин — 429 (счёт в Redis; адрес — `X-Real-IP`
  от прокси перед API). У всех ответов — `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer`. При `MM_ENV=prod` процессы backend не стартуют со значениями из `.env.example`
  (ADR 0010).
- Аутентификация: вход по логину и паролю (JWT); пользователи и роли в БД (п. 7.3). Суперадмин создаётся при
  первом старте из `.env`. Киоск — device-токен, привязанный к одному станку (экран оператора) или одному
  участку (ТВ-дашборд); в БД хранится только хеш, токен выдаёт и отзывает администратор.
- OpenAPI-схему строит FastAPI. TypeScript-клиент пока написан вручную (`frontend/src/api/client.ts`); генерация из OpenAPI — когда у маршрутов появятся модели ответов.

### 7.3. Роли и проверка доступа
Роль выдаётся на узел иерархии (`memberships`): только `org_id` — вся организация, с `site_id` — площадка,
с `area_id` — участок. Права ролей заданы в коде одной таблицей (`app/core/access.py`), настраиваемой матрицы нет.

| Роль | Доступ |
|---|---|
| `operator` | станки узла: экран оператора — причина простоя, брак, наладка |
| `master` | участок: дашборд, аналитика и журнал аварий, правка причин простоя и брака, справочники на чтение, отметка «столкновение», заявки на ремонт и график обслуживания |
| `engineer` | площадка: нормы цикла, аналитика и журнал аварий, справочники на чтение, состояние коллекторов, заявки на ремонт и график обслуживания |
| `admin` | организация: станки, участки, площадки, коллекторы, смены, справочники, пользователи, токены киосков, журнал аварий, заявки на ремонт и график обслуживания |
| `service` | сотрудник сервисной компании: станки, состояния, аналитика, журнал аварий и коллекторы всех организаций; ведёт заявки на ремонт и регламенты обслуживания (ADR 0006); внутренний архив геометрии — тесты ballbar, тренды, отметки «столкновение», журнал ремонтов (ADR 0005) |
| суперадмин | всё, создание организаций и назначение роли `service` |

Проверка доступа — в одном месте: зависимость API `get_scope` по токену строит область доступа
(станки по каждому праву, видимые площадки и организации). Каждый маршрут и `/ws/live` работают внутри неё;
сервисные функции принимают список станков или площадок явным параметром. Объект вне области — 404,
действие без права внутри области — 403.

Управление пользователями. Роль выдаётся только на узел, где у вызывающего есть `users.manage`.
Сменить пароль, имя, отключить учётную запись или снять роль можно только у пользователя, **все** роли
которого (во всех организациях) лежат в таких узлах: администратор площадки не трогает администратора
организации, администратор организации B — человека, у которого есть роли и в A. Такими учётными записями,
а также сотрудниками сервиса и пользователями без ролей, управляет суперадмин. `GET /users` отдаёт признак
`manageable`, интерфейс по нему скрывает недоступные действия.

с `MM_ENV=prod`, `MM_DEMO_DATA=false`, `MM_PUBLIC_URL=https://MM_DOMAIN`. Добавляются:

| Сервис | Образ | Назначение |
|---|---|---|
| `caddy` | caddy:2.11.9-alpine | HTTPS для `MM_DOMAIN` (Let's Encrypt, продление само), 80 → 443; `/api/*`, `/ws/*` — в API, остальное — в `web` |
| `backup` | `deploy/backup/Dockerfile` (TimescaleDB 2.32.0-pg16 + rclone 1.76.0) | ночной `pg_dump` в S3-совместимое хранилище, хранение 30 дней; `make backup-now`, `restore`, `restore-check` |
| `restore-check-db` | timescale/timescaledb:2.32.0-pg16, профиль `tools` | временная чистая база для `make restore-check` |

Наружу в prod — только 80 и 443 (Caddy) и 8883 (Mosquitto, TLS). «Демо-предприятие» миграций удаляется
`make prod-drop-demo`. Запланировано (этап 6), пока нет: `prometheus` и `grafana` (профиль `monitoring`).

### 8.2. Edge
Коллектор, конфиг `config.yaml`, том для буфера; образ — `edge/Dockerfile` (Linux). Сеть коллектора и проверка
связи со стойкой — `docs/runbooks/collector-network.md`. Запланировано, пока нет: compose-файл для площадки
(`deploy/docker-compose.edge.yml`) и установщик Windows.

### 8.3. Сеть и безопасность
- Сеть станков (OT) отделена от офисной (IT). Коллектор стоит на границе: FOCAS — в OT, MQTT — исходящее соединение в сторону сервера.
  Коллектор ставится в сеть станков или в подсеть, откуда открыт TCP 8193 до стоек; VPN и туннельных программ
  на его ПК нет (`docs/runbooks/collector-network.md`).
- Наружу с сервера (prod) открыты только 80 и 443 (Caddy, HTTPS) и 8883 (MQTT по TLS для коллекторов); БД, Redis,
  API, web и 1883 — только внутри сети compose.
- Необходимый минимум (ADR 0010): отказ старта со значениями паролей из `.env.example`, ограничение попыток входа,
  заголовки безопасности, токен киоска убирается из адресной строки, ночные бэкапы с проверкой восстановления.
- Секреты — в `.env` / переменных окружения, не в git.
- Изоляция клиентов — фильтром по области доступа в API. Row-level security в БД, журнал входов сервисных
  инженеров и согласие клиента на доступ сервиса не делаются на этом этапе.

### 8.4. Наблюдаемость
- Есть: структурированные JSON-логи; состояние коллекторов (heartbeat, буфер, разрывы `seq`) — `GET /api/v1/collectors`
  и раздел админки; счётчики приёма раз в 30 с в логе `ingest`.
- Запланировано (этап 6), пока нет: Prometheus-метрики (backend `/metrics`, задержка приёма, очередь пересчёта,
  коллекторы) и Grafana-дашборд «Здоровье системы».

## 12. Решения, от которых сознательно отказались (на старте)

| Не делаем | Почему |
|---|---|
| Микросервисы / Kubernetes | Масштаб 10–200 станков не требует; модульный монолит выносится в сервисы позже |
| Kafka | MQTT + PostgreSQL достаточно; лишний компонент эксплуатации |
| Отдельная InfluxDB | TimescaleDB закрывает временные ряды в той же БД |
| Celery / RabbitMQ | Очередь задач на PostgreSQL (`SKIP LOCKED`) |
| Логика на edge | Обновление и отладка сложнее; правила должны пересчитываться централизованно |
| Keycloak на старте | Встроенный JWT + RBAC; SSO/LDAP — отдельным этапом при необходимости |
| Отдельная база на клиента, RLS | Одна база и фильтр в API проще в эксплуатации; RLS — при требованиях клиентов |
| Настраиваемая матрица прав | Пять ролей с правами в коде покрывают сценарии; матрица — при реальной потребности |
