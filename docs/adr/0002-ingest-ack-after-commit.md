# ADR 0002. Ingest подтверждает MQTT-сообщение только после фиксации в БД

- Статус: принято
- Дата: 2026-11-16

## Контекст

Принцип «ни одной потерянной секунды» должен выполняться и на участке брокер → БД.
По умолчанию MQTT-клиент отправляет PUBACK сразу при получении сообщения: если
процесс `ingest` упадёт между получением и `COMMIT`, сообщение будет потеряно.
Кроме того, на чистом брокере без постоянной сессии сообщения, пришедшие во время
простоя `ingest`, никому не доставляются.

## Решение

1. `ingest` подключается по MQTT v5 с постоянной сессией (`clean_start=false`,
   фиксированный `client_id`, `SessionExpiryInterval` 7 суток) — брокер копит
   QoS 1 сообщения, пока `ingest` остановлен.
2. Подтверждение ручное: PUBACK отправляется после успешного `COMMIT` пакета.
   При ошибке БД пакет повторяется с задержкой 1 → 30 с и не подтверждается.
   Повторная доставка безопасна благодаря идемпотентной записи (ADR 0001).
3. В `aiomqtt` нет публичного API ручного подтверждения, поэтому используется
   нижележащий клиент paho (`manual_ack_set` / `ack`), обращение изолировано в
   `app/ingest/consumer.py`.
4. В Mosquitto `max_inflight_messages 500`: окно неподтверждённых сообщений
   ограничивает размер пакета записи.

## Последствия

- Каждому экземпляру `ingest` нужен свой `MM_INGEST_CLIENT_ID`.
- Shared subscription (`$share/ingest/mm/v1/#`) оставлена, как в архитектуре, но
  при нескольких экземплярах порядок сообщений одного станка не гарантируется.
  Для сырых данных это не важно; для state machine (этап 3) вопрос надо решить
  отдельно — до тех пор запускается один экземпляр.
- Зависимость от приватного атрибута `aiomqtt.Client._client`; версия `aiomqtt`
  ограничена `<3`, поведение покрыто проверкой перезапуска в отчёте этапа 1.
