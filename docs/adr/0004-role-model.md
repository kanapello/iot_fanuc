# ADR 0004. Модель ролей и проверка доступа

- Статус: принято
- Дата: 2026-11-17

## Контекст

Пользователи разных организаций работают в одной установке. Внутри организации доступ различается по
узлам: мастер видит свой участок, технолог — площадку, администратор — организацию. Сотрудники
сервисной компании видят станки всех клиентов. Экраны в цеху (планшет оператора, ТВ) работают без входа.

## Решение

1. **Роль выдаётся на узел иерархии**: таблица `memberships (user_id, role, org_id, site_id, area_id)`.
   Только `org_id` — вся организация, с `site_id` — площадка, с `area_id` — участок. У пользователя
   может быть несколько строк. Роль `service` выдаётся без узла и действует во всех организациях.
2. **Права ролей заданы в коде одной таблицей** (`app/core/access.py`): `operator`, `master`, `engineer`,
   `admin`, `service`; суперадмин — флаг пользователя. Настраиваемой матрицы прав нет.
3. **Одно место проверки.** Зависимость API `get_scope` по токену строит объект `Scope`: станки по каждому
   праву, видимые площадки, организации и участки, роли на узлах. Маршруты и `/ws/live` работают только
   внутри него; сервисные функции принимают область доступа (список станков или площадок) явным параметром,
   функции фоновых процессов помечены `*_system`.
4. **Чужой объект — 404, не 403.** Объект вне области доступа для пользователя не существует; 403 —
   только когда объект виден, но действие не разрешено ролью. Фильтры запросов (`site_id`, `area_id`,
   `machine_id`) только сужают область.
5. **Киоски.** Токен устройства привязан к одному станку (экран оператора: просмотр и ввод оператора)
   или одному участку (ТВ: только просмотр). В БД хранится SHA-256 токена; выдаёт и отзывает
   администратор. Общий токен из `.env` убран.
6. **Live-канал** Redis — на площадку (`live.{org}.{site}`); API пересылает клиенту только станки
   его области, потому что внутри площадки область может быть уже (участок, станок).
7. Суперадмин создаётся при первом старте API из `MM_ADMIN_USERNAME` / `MM_ADMIN_PASSWORD`. Только он
   создаёт организации и назначает роль `service`.

## Последствия

- Изоляция держится на API. Row-level security в БД, журнал входов сервисных инженеров и согласие клиента
  на доступ сервиса не делаются на этом этапе (см. `NOW.md`).
- Тест изоляции перебирает **все** маршруты API: новый маршрут без записи в тесте его роняет.
- Пароли — scrypt; сессия — JWT без отзыва (отключённый пользователь теряет доступ сразу, потому что
  пользователь проверяется в БД на каждый запрос).
- Действия оператора по-прежнему подписываются текстовым полем `operator`; PIN и табельный номер — позже.
