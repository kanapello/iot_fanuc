# ADR 0001. Ключ идемпотентности сырых данных — `(msg_id, ts)`

- Статус: принято
- Дата: 2026-11-16

## Контекст

`ARCHITECTURE.md` (п. 5.2, 5.3) описывал идемпотентный приём как
`INSERT ... ON CONFLICT (msg_id) DO NOTHING` при `msg_id (unique)` в таблице `telemetry`.
`telemetry` и `machine_events` — hypertable TimescaleDB, секционированные по `ts`.
TimescaleDB не позволяет создать уникальный индекс, в который не входит колонка
секционирования: уникальность проверяется внутри чанка, а не по всей таблице.

## Решение

Первичный ключ обеих сырых таблиц — `(msg_id, ts)`, приём —
`ON CONFLICT (msg_id, ts) DO NOTHING`.

Идемпотентность сохраняется: повторно доставленное сообщение (MQTT QoS 1, повтор
из буфера edge) несёт те же `msg_id` и `ts`, потому что конверт формируется
один раз в момент чтения со стойки и дальше не меняется.

## Последствия

- Два сообщения с одинаковым `msg_id`, но разным `ts` будут записаны оба. Для
  исправного коллектора это невозможно (`msg_id` — UUIDv7, генерируется вместе с `ts`).
- Edge обязан хранить в буфере готовый конверт, а не пересобирать его при повторной
  отправке (учесть на этапе 2).
- `ARCHITECTURE.md`, п. 5.2 и 5.3, обновлён.
