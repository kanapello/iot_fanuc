# Отчёт: уведомления в Telegram (feat/notifications)

Дата: 2026-11-25 · Ветка: `feat/notifications` · Решение: ADR 0011 · Настройка: `docs/runbooks/cloud-install.md`, раздел 4

## Итог

Пользователь подключает Telegram в профиле: одноразовая ссылка на бота, «Запустить» — и его чат привязан. Дальше ему
приходят события его ролей и только по его станкам. Авария — мастеру участка и сервису; батарея и вентилятор — сервису;
коллектор без связи и потерянный буфер — сервису и администратору организации; простой без причины — мастеру; новая
заявка — сервису; смена её статуса — администратору и мастеру; подходящее ТО — сервису. Одно событие станка — не чаще
раза в 15 минут; когда авария снята или коллектор вернулся, приходит короткое «восстановлено». Сообщения идут через
очередь в PostgreSQL с повторами; бот работает через long polling, публичный адрес не нужен; ошибки Telegram worker не
роняют.

## Что сделано

| Часть | Содержание |
|---|---|
| Хранение | Миграция `0012`: `areas.stop_alert_minutes` (10), `telegram_chats` (один пользователь — один чат), `telegram_link_codes` (хеш, 15 мин), `notification_mutes`, `notification_conditions` (антиспам, «восстановлено»), `notification_outbox`, `notification_cursors` |
| Модуль `app/notify` | `telegram.py` — Bot API (`sendMessage`, `getUpdates`), токен не пишется в лог; `events.py` — типы, роли, тексты на русском со ссылками на `MM_PUBLIC_URL`; `store.py` — таблицы; `service.py` — `Notifier`: условия, получатели, отправка, бот |
| Условия | авария и предупреждения — по `alarm_code` свежей (≤ 10 мин) телеметрии; коллектор — по heartbeat дольше 5 мин и `buffer_lost_at`; простой — STOP дольше порога участка без причины (таймлайн и аннотации); заявки — по истории с курсора; ТО — по графику наработки (раз в 5 мин). Данные других модулей — через их сервисные функции |
| Получатели | область доступа пользователя строится так же, как для API (`identity.user_scope`, общий код с `load_scope`), плюс роль события, выданная на узле станка или площадки (`Scope.roles_on_machine` / `roles_on_site`); выключенные типы не приходят |
| Отправка | `FOR UPDATE SKIP LOCKED`, чат — в момент отправки; повторы 10 с, 30 с, 1, 5, 15, 30 мин или по `retry_after`, 8 попыток; 403 (бот заблокирован) — чат отвязывается |
| Бот | long polling в `worker`; `/start <код>` — привязка (только личный чат, код одноразовый), `/stop` — отвязка, остальное — подсказка |
| API | `GET /profile/telegram`, `POST /profile/telegram/link`, `DELETE /profile/telegram`, `GET` и `PUT /profile/notifications` — только своя учётная запись, устройства — 403; все пять — в тесте изоляции |
| Интерфейс | «Профиль» (имя в шапке): подключить и отвязать Telegram, флажки типов своих ролей; ролям без уведомлений — пояснение вместо кнопки. Админка → «Участки»: порог простоя. Журнал аварий открывается по ссылке из уведомления на станке и эпизоде (`/alarms?machine=…&at=…`) |
| Настройка | `MM_TELEGRAM_BOT_TOKEN`, `MM_TELEGRAM_BOT_USERNAME`, `MM_NOTIFY_REPEAT_MINUTES` в `.env.example` и compose; без токена уведомлений нет |

## Найдено по ходу

| Что | Как нашлось | Что сделано |
|---|---|---|
| Тестовая очистка базы не трогала таблицы без ссылок на пользователей: состояние «авария активна» переживало тест и давало чужое «восстановлено» | тесты | `notification_conditions` и `notification_cursors` — в `TRUNCATE` фикстуры |
| В `users` нет столбца `name`: исполнителя заявки читаю из самой заявки | тесты | `repair_requests.executor_name` |
| Ролям без уведомлений (технолог, оператор) профиль предлагал подключить Telegram впустую | браузер | вместо кнопки — «Для ваших ролей уведомлений нет» |
| `httpx` был только тестовой зависимостью | сборка | перенесён в рабочие зависимости backend |

## Решения, которые стоит подтвердить

- **Технолог и оператор** по постановке уведомлений не получают; суперадмин без ролей — тоже.
- **«Восстановлено» для простоя без причины** — когда станок снова работает или причина указана (в тексте — что
  именно); для ТО и заявок «восстановлено» нет.
- **События до подключения** не досылаются: начало, объявленное без получателей, считается объявленным.
- **Батарея и вентилятор** — один тип `warning`; смена одного на другое без снятия — тот же эпизод.
- **Ссылка из уведомления о простое** ведёт на экран оператора станка: там мастер сразу укажет причину.
- **Поздние данные не новость**: авария в телеметрии старше 10 минут не объявляется, потерянный буфер — в течение часа.
