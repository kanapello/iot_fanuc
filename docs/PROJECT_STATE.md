## 1. Что строим и бизнес-модель

- Система мониторинга станков с ЧПУ класса MachineMetrics: состояния, таймлайн, OEE, простои с причинами,
  циклы, аварии, ремонты. Первая стойка — **Fanuc 0i-MD** (FOCAS2).
- **Сервис для многих предприятий** (мультитенант) у сервисной компании. Продаётся **в комплексе** с аварийным
  ремонтом станков и контролем геометрической точности (Renishaw QC20 ballbar): клиенты не хотят платить за
  мониторинг отдельно, а в комплексе с сервисом это преимущество.
- Сервер — в облаке у **российского** провайдера (152-ФЗ). Тот же Docker Compose ставится у клиента.
- Коллектор в цеху — промышленный безвентиляторный мини-ПК **x86** с двумя сетевыми портами (сеть станков и
  выход к серверу), Linux + Docker. Под 64-битный ARM библиотеки FOCAS нет.
- Репозиторий https://github.com/kanapello/iot_fanuc — **публичный** (сделать приватным — решение владельца,
  не принято).

## 2. Как работаем

- **Владелец** принимает решения и проверяет результат. **Чат-ассистент** проектирует, проверяет ветки и PR,
  готовит промпты. **Claude Code** пишет код по промптам и документам (`ARCHITECTURE.md`, `CLAUDE.md`,
  `NOW.md`, этот файл) и сам сливает PR.
- Каждая задача — своя ветка и PR; слияние merge commit (не squash), только при зелёных `make lint`,
  `make test` и CI (8 проверок: `backend`, `edge`, `frontend`, `deploy`, `image (backend|web|edge|backup)`).
- В начале задачи — короткий план, в конце — отчёт в `docs/<задача>-report.md` (с разделом «Решения, которые
  стоит подтвердить»), обновлённые `NOW.md`, `ARCHITECTURE.md`, ADR на решения (`docs/adr/`) и этот файл.
- Новые маршруты API — в тест изоляции организаций (`backend/tests/test_tenancy.py`). Производные данные —
  пересчитываемые (правило 2 `CLAUDE.md`). Система по отношению к стойке только читает.
- Язык: код и коммиты — английский; документы и общение — русский; тексты интерфейса — русский через i18n.
- Не коммитить: `fwlib64.cs` (авторские права Fanuc), `Fwlib*.dll`, `libfwlib32.so`, `.env`, `edge/vendor/`,
  `edge/data/`.
- Облачная среда Claude Code не может менять настройки репозитория, ставить теги, удалять ветки на GitHub и
  выходить к части внешних сервисов (например, к API Telegram) — это делает владелец.

**Просмотр у владельца.** Windows 10 + Docker Desktop с WSL (понадобилось включить компоненты
VirtualMachinePlatform и Subsystem-Linux, поставить WSL и перезагрузиться). Git не установлен: код скачан


Интерфейс — http://localhost:8080, демо-учётные записи — в `README.md`. Обновление: заново скачать архив `main`,
перенести `.env`, пересобрать той же командой.

## 3. Решения владельца (не пересматривать без причины)

- **Безопасность сверх необходимого не усиливать.** Отклонены: row-level security, согласие клиента на сервисный
  доступ, журнал входов сервиса, журналы аудита. Перед первым внешним клиентом — только минимум: HTTPS/TLS, без
  паролей по умолчанию, бэкапы, ограничение попыток входа, заголовки (сделано в #18).
- **Геометрия** — только архив и тренд, без анализа (допуски, политики проверок, автоматический разбор `.b5r`
  удалены). Видит **только роль `service`**. Оператор и мастер могут поставить отметку «столкновение», но не видят
  архив.
- **Ремонты:** клиент видит свои заявки и график ТО и создаёт заявки; журнал ремонтов и геометрия — только сервис.
- **Сухие контакты (Modbus TCP)** — отложено, пока не запущена хотя бы одна стойка Fanuc.
- **Опрос стойки осторожный:** по умолчанию минимум (статус, программа, счётчик деталей, аварии); подача,
  обороты, нагрузки, коррекции, PMC — только после измерений на живой стойке (ADR 0007).
- **Новых функций не делать, пока не заработает первая стойка;** если доступа к станку нет — облако и уведомления
  (сделаны). Исключение, которое владелец сделал после просмотра интерфейса, — главный экран-сводка
  (`feat/overview-dashboard`).
- **Хранение телеметрии:** 2 года, сжатие через 30 дней. Короткий срок (7–14 дней) отклонён: ломает пересчёт
  таймлайна и OEE. Короткий срок допустим только для будущих быстрых потоков (PMC, нагрузки осей).
- **Уведомления — только Telegram;** почта, вебхуки и SMS не делаются.

## 5. Реальная стойка — этап 0 не закрыт

**Стойка:** Fanuc 0i-MD, Ethernet настроен на стойке, FOCAS2 на штатном порту 8193. Сеть станков — отдельная
подсеть.

**Что выяснили:**
- На заводском ПК (в офисной сети) есть 64-битная библиотека FOCAS2 (`Fwlib64.dll` и библиотеки серий) и
  64-битный Python.
- Ошибка `EW_NODLL` была из-за поиска соседних DLL — исправлено в #9.
- На ПК стоит программа с туннельным адаптером (Wintun), который забирает весь трафик. Через него пинг и
  проверка порта «успешны», но FOCAS отвечает `EW_SOCKET`.
- Без туннеля маршрутизатор офисной сети отвечает «Заданный узел недоступен»: подсеть станков не маршрутизируется
  из офисной (или закрыта).
- LADDER-III с этого ПК тоже не подключается к стойке.
- Вывод: проблема в сетевом пути, не в пробе и не в стойке.

**Следующий шаг:** ноутбук кабелем в сеть станков (коммутатор шкафа или прямо в стойку) со свободным статическим
адресом из подсети станков (согласовать с ИТ, маску — как у стойки). Порядок: `ping` → `Test-NetConnection -Port
8193` → проба минимум с `--watch --out` → один запуск `--recon`. Сценарий: станок стоит, цикл одной детали,
стоп подачи, смена режима, ручки коррекции, смена инструмента; сверить с экраном стойки. По шагам —
`docs/runbooks/first-machine.md`.

**Для коллектора:** ставить в сеть станков или просить ИТ открыть TCP 8193 из его подсети; на ПК коллектора —
без VPN и туннелей (`docs/runbooks/collector-network.md`).

**Полезные факты:**
- `cnc_statinfo`: `alarm` 1 — авария, 2 — батарея, 3 — вентилятор; `emergency` 1 — аварийный стоп, 2 — сброс.
  В системе авария — только код 1; коды 2 и 3 идут в уведомления сервису (#19).
- Структуры пробы совпадают с официальным `fwlib64.cs` от Fanuc (`ODBST`, `ODBEXEPRG`, `ODBM`, `LOADELM`,
  `ODBALMMSG2`). Сам `fwlib64.cs` не коммитить.
- Из руководства Kepware: `cnc_rdtimer` (наработка стойки с первого дня), `cnc_rddynamic2` (много данных одним
  вызовом), `cnc_rdaxisdata`, `cnc_rdprogdir3`; число одновременных подключений FOCAS у стойки ограничено.
- Код коллеги на C# читает сигнал PMC `F0.7` (идёт автоматическая работа) — кандидат в признак RUN.

## 6. Дорожная карта

```
проба на стойке → облако (#18) → уведомления (#19) → пилот у 2–3 клиентов по ремонту
(бесплатно, за обратную связь) → функции по отзывам пилота
```

- **Главный экран-сводка — слито (#21)** (`feat/overview-dashboard`, отчёт `docs/overview-report.md`, ADR 0012): меню
  слева; карточки «Загрузка», «OEE», «Производительность», «Доступность» с изменением к прошлому периоду и обычным
  уровнем; выпуск; станки сейчас; простои по причинам; «загрузка ниже обычной»; «циклы медленнее нормы»; боковая
  панель станка. Для демо симулятор досылает 21 день истории (28 не уложились в 10 минут `make up`).
- **Инфраструктура до пилота (владелец):** VM у российского провайдера, домен, S3-бакет, бот через `@BotFather`;
  установка и чек-лист — `docs/runbooks/cloud-install.md`; проверка уведомлений с настоящим Telegram.
- **Функции после пилота** (из заметок владельца): коррекции подачи и шпинделя, «чёрный ящик» PMC, архив бэкапов
  стойки и сравнение параметров, автоучёт наладки, нагрузка по инструменту, деградация узлов, автоопределение
  столкновений (только по накопленным данным), сухие контакты.
